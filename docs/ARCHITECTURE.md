# ORACLE architecture

```text
explicit `mrginu` invocation
  ├── detached monitor daemon (flock + proc start-time identity)
  │     └── bounded psutil polling → local resource sampler + local heuristic rules → SQLite
  │            ├── event ≥ threshold → deterministic investigation → bounded Groq review queue
  │            └── resource alert → bounded independent investigation / notify-send / Timbre workers
  └── optional `mrginu --dash`
        ├── FastAPI (127.0.0.1:8000) → SQLite and Groq case chat/review
        └── Vite (127.0.0.1:5173) → React dashboard → alert inbox, persisted settings, transcript confirmation
              └── explicit audio upload / report playback and alert replay → Gnani STT/TTS
```

The monitoring daemon is separate from the backend and browser. Its first pass establishes a process baseline; subsequent process identities use `(PID, create_time)` to avoid treating reused PIDs as the same process. It keeps a bounded in-memory identity map and polls at the configured interval. A local resource sampler writes system counters every five seconds by default and a bounded set of process metrics every fifteen seconds. System and process resource samples are stored in additive SQLite tables with timestamp/identity indexes and configurable time retention. Resource reads are served by the loopback API for the dashboard timeline. Heuristics are local and run before optional model analysis. Automatic model reviews have a bounded queue; the collector never waits on a network request.

SQLite connections use WAL, a busy timeout, indexes, age-based retention, and event/investigation caps. Chat context is stored per investigation, limited to eight turns, and pruned with old investigations. The CLI stores its lock and managed process records in the user's state directory. PID records include Linux `/proc` start time and a command marker; services started by the CLI use isolated process groups. No boot unit is installed.

Investigation inspection is fixed to `psutil` process details, parent details, and network endpoints. The reasoning adapter sends an allowlisted case bundle to Groq; it omits usernames and command lines and redacts usernames embedded in `/home/...` paths. Case chat includes only the selected investigation and four previous turns. No model tool calls or shell execution are enabled. AI report fields are explicitly inference; local heuristic output and collected facts are separate. Groq failures do not replace or invalidate the deterministic report.

`detection.py` evaluates process samples after they are persisted. It waits for configured baseline and observation periods, compares CPU with a median/MAD bound, requires substantial absolute and relative RSS growth, and requires a newly observed endpoint to persist. It records observations and baselines in an additive `alerts` table, deduplicated by detector and process identity during cooldown. Corroborating signals can raise severity; one CPU spike remains low. `/api/alerts` serves state and evidence, while the dashboard supplies filtering and lifecycle actions.

The daemon starts independent bounded workers for automatic investigation linking, desktop notifications, and spoken alerts. Each alert row is the durable work record: queue overflow and daemon restarts are recovered by worker polling, and delivery attempts/retry times are stored in SQLite. Investigation linking uses a deterministic event ID derived from the alert ID, a persisted `investigations.event_id`, and an in-process lock; after a crash it checks for an existing investigation before creating one. Resource-alert events record PID plus creation time, and the investigation collector refuses to attach current process details if that PID has been reused. Notification delivery invokes `notify-send` without a shell, applies severity and cooldown settings, and records success only after the notification command succeeds. Failures are nonfatal and retried a bounded number of times. An optional click action opens the local linked investigation URL when the dashboard is reachable.

Worker threads are supervised by the daemon. Idle queue-recovery errors are logged and retried instead of escaping the thread loop; the daemon checks worker liveness and restarts an exited worker. Worker heartbeats are stored in `daemon_worker_status`. `/api/health` reports the API database path, expected daemon PID, heartbeat freshness, worker state, and last recovery error so a split API/daemon database is observable. Retry timestamps represent a deliberate delay and pending records are queried again on idle polling once those timestamps are due.

Timbre uses a separate bounded worker queue and reuses `_speak_once`, preserving the configured endpoint, auth, model, and WAV validation. `provider_state` in SQLite gives the daemon and API one single-flight lease and persists provider retry time. Rate-limit retries are bounded per alert. Generated WAV bytes are capped at 1 MB and stored locally; `pw-play` is preferred for playback, then `aplay` or `paplay`. The worker writes a mode-0600 temporary WAV, starts the player without a shell and without provider credentials, enforces a timeout, and removes the file even on failure. It marks the alert spoken only after the audio player exits successfully; a playback failure reuses the saved WAV instead of spending another TTS request. Cooldown starts only after successful playback. At most 100 clips are retained for replay. Provider and audio failures never block resource sampling or notification delivery.

The additive schema migration adds event links to existing investigations/alerts, provider coordination state, and notification/synthesis/playback retry state on first database open. Alert retention has both age and hard-count limits; resource history remains time bounded. Existing records are preserved. Alert status transitions are served by `/api/alerts`; settings changes are stored in `app_settings` and shared by daemon/API processes, so notification and speech controls take effect on the daemon's next settings poll without a restart.

`POST /api/alerts/test` creates a synthetic HIGH alert only while the daemon is active. It has a one-minute test-only cooldown, no PID, and explicit synthetic evidence; it never starts or inspects a process or connects externally. The daemon's normal workers deliver it using current notification and speech preferences. `GET /api/alerts/{id}/delivery` reports persisted notification, synthesis, playback attempt, and success state for the test. `played` means the desktop audio player exited successfully; hardware output cannot be sensed by ORACLE. The dashboard labels test data and polls this endpoint after a test.

Gnani is a separate speech integration: Prisma converts explicitly recorded audio to text, and Timbre converts report text to audio. It is not the reasoning provider. The API is unauthenticated and should remain loopback-only. The demo event is synthetic and remains marked as such.

Prisma's transcription endpoint returns text only; `/api/voice/command` runs only after a separate user confirmation and routes a fixed allowlist (inspect/explain a case or alert, summarize stored resource history, or existing investigation commands). No transcript is passed to a shell. Groq evidence bundles for alert investigations include only capped, allowlisted system/process samples from the alert window, related local events, detector evidence, and explicit history gaps. Groq may return a timeline and safe interpretation, but observations remain separate and unavailable measurements are not filled in.
